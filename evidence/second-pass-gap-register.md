## How to use this register

Each row identifies the highest-value unresolved work in the existing review and the official online sources already available for that work. “High” means a loss-of-control, exit, recovery, or integrity claim should be tested before softer questions such as telemetry or governance. The next action is deliberately operational: run the smallest disposable-data experiment that can establish or refute the claim, record the exact version and environment, and then update the entry only with evidence-backed findings.

The online sources below are current documentation evidence, not independent verification:

- [Zotero data directory and backup guidance](https://www.zotero.org/support/zotero_data) says the database and storage folder must be copied with Zotero closed, and warns that export formats are not a proper backup.
- [Joplin import/export](https://joplinapp.org/help/apps/import_export/) describes JEX as a tar-based, re-importable format that preserves notes and metadata.
- [Git bundle format](https://git-scm.com/docs/bundle-format) documents prerequisites that the receiving repository must already have; this is a concrete exit/recovery condition to test.
- [Org mode manual](https://orgmode.org/org.html) confirms plain-text editability and documents export behavior, including Babel evaluation; this makes structure preservation and execution controls separate tests.
- [restic troubleshooting](https://restic.readthedocs.io/en/stable/077_troubleshooting.html) documents interruption and corruption-recovery behavior, while [Borg check](https://borgbackup.readthedocs.io/en/2.0.0b23/usage/check.html) documents encrypted verification and repair boundaries.
- [todo.txt format](https://github.com/todotxt/todo.txt) confirms the human-readable, line-oriented interchange model, but client behavior and recoverability still require cross-client tests.
