Reviewed 23 October 2026, Asia/Baghdad. Fourteen specific questions are resolved across CadQuery, darktable, JabRef, GNU Octave, Kdenlive, and KeePassXC. The six application assessments include these findings and the remaining work.

python evidence/third-pass/batch-2/inspect_artifacts.py

Upstream copyright and license notices remain in the retained source files; fixture files remain subject to upstream licensing. No target application or downloaded script was executed, and no CI result is claimed. Fixtures can be historical even when retained in a current source tree.

## CadQuery

- [x] Resolved: can a published STEP sample expose product names and colour records without CadQuery? The [retained sample](https://github.com/CadQuery/cadquery/blob/33361dc1b5b70bc83ce36f1b34a01ca85dfca80a/tests/testdata/red_cube_blue_cylinder.step) is readable ISO-10303-21 text. It contains `blue_cylinder` and `red_cube` product records, two `MANIFOLD_SOLID_BREP` entities, and nine `COLOUR_RGB` records. This inspects metadata and entity records, not reconstructed geometry. The [assembly exporter](https://github.com/CadQuery/cadquery/blob/33361dc1b5b70bc83ce36f1b34a01ca85dfca80a/cadquery/occ_impl/exporters/assembly.py#L104-L132) explicitly enables colour, layer, and name modes. The sample's upstream origin does not establish that it was generated by the inspected exporter, and receiving-tool fidelity remains untested.
- [x] Resolved: does CQGI treat model input as executable Python or only declarative geometry? Its [build implementation](https://github.com/CadQuery/cadquery/blob/33361dc1b5b70bc83ce36f1b34a01ca85dfca80a/cadquery/cqgi.py#L104-L125) installs real builtins, compiles the model, and calls `exec`; exceptions are captured in the build result. This is an executable model boundary, not evidence of a sandbox.

Remaining: constraints and editable intent in another CAD tool, geometry equivalence, complete offline rebuild, dependency versions, and actual execution/overwrite safeguards.

## darktable

- [x] Resolved: can the contents of an XMP edit history be inspected independently? Standard XML parsing of the [4.2 benchmark sidecar](https://github.com/darktable-org/darktable/blob/6556cd7dbb0e69f95d165dda8b69e7270c327f6d/src/tests/benchmark/darktable-bench-4.2.xmp) yielded 69 history entries with operation names and module versions. The sidecar contains edit structure beyond an embedded preview.
- [x] Resolved: is the parameter encoding available and decodable? The [encoder/decoder](https://github.com/darktable-org/darktable/blob/6556cd7dbb0e69f95d165dda8b69e7270c327f6d/src/common/exif.cc#L3649-L3785) uses hex or a `gz` prefix with a two-digit compression factor followed by Base64/zlib data. The inspection decoded and hashed 160 parameter/mask blocks, including 95 compressed blocks. Decoded bytes still require module-specific interpretation to reproduce an image.

Remaining: render equivalence, full library organization, DTDATA and current-module semantics, database reconstruction, database/sidecar precedence, and version compatibility.

## JabRef

- [x] Resolved: can group hierarchy be recovered from a real `.bib` fixture without JabRef? The [retained library](https://github.com/JabRef/jabref/blob/1e2e9a089986e317cd7f82f4c0114b8950164925/jabsrv/src/test/resources/org/jabref/http/server/groups-server-test.bib) has two bibliographic records and a `jabref-meta: grouping` comment. Four named groups and the root are readable, including `Papers` with children `2024` and `Machine Learning`. The [serializer](https://github.com/JabRef/jabref/blob/1e2e9a089986e317cd7f82f4c0114b8950164925/jablib/src/main/java/org/jabref/logic/exporter/GroupSerializer.java#L96-L109) writes a depth followed by the group representation and recurses through children. This does not establish the membership of every entry.
- [x] Resolved: how are associated-file details encoded? [`FileFieldWriter`](https://github.com/JabRef/jabref/blob/1e2e9a089986e317cd7f82f4c0114b8950164925/jablib/src/main/java/org/jabref/logic/bibtex/FileFieldWriter.java) serializes description, link, file type, and optionally source URL, with colon-separated components, semicolon-separated files, and backslash escaping. This specifies how to interpret the field; it does not establish that linked files exist or are copied with a library.

Remaining: custom types and fields, group membership, another reader's treatment of JabRef comments, actual path relocation, backups, and cross-version rewrites.

## GNU Octave

- [x] Resolved: can actual saved matrices be read without Octave? The [penny](https://github.com/gnu-octave/octave/blob/5208f34c2b13b447c68c956be2a0b1d67476a80d/examples/data/penny.mat) and [west0479](https://github.com/gnu-octave/octave/blob/5208f34c2b13b447c68c956be2a0b1d67476a80d/examples/data/west0479.mat) fixtures use Octave text despite their `.mat` suffixes. Python read a 128-by-128 dense matrix with 16,384 values and a 479-by-479 sparse matrix with 1,888 stored values. Header dimensions, row widths, sparse coordinate bounds, and unique coordinates were validated. Creator headers identify Octave 3.8.1 and 5.2.0; this is not binary MAT/HDF5 compatibility testing.
- [x] Resolved: what does the plain ASCII save implementation lose, and is that surfaced? [`save_mat_ascii_data`](https://github.com/gnu-octave/octave/blob/5208f34c2b13b447c68c956be2a0b1d67476a80d/liboctinterp/load-save/ls-mat-ascii.cc#L335-L354) emits warnings for omitted imaginary components and skips variables with more than two dimensions. Plain ASCII and Octave text are different save formats.
- [x] Resolved: does the inspected save implementation always overwrite the destination directly? The [main save path](https://github.com/gnu-octave/octave/blob/5208f34c2b13b447c68c956be2a0b1d67476a80d/liboctinterp/load-save/load-save.cc#L1564-L1670) uses a `.saving_in_progress` file followed by rename for non-append saves. Append mode writes directly. This identifies the implementation, not crash durability or the destination's behavior on every filesystem.

Remaining: complex/struct/classdef preservation, binary MAT and HDF5 round trips, seeded numerical reproduction, package dependencies, and actual save failures.

## Kdenlive

- [x] Resolved: can a project with nested editing structures and effects be inspected without Kdenlive? The [retained fixture](https://github.com/KDE/kdenlive/blob/80b74ffa95390f4cc8d75a4e886e7ff47373583e/tests/dataset/test-nesting-effects.kdenlive) parsed as MLT XML, reporting document version `1.1`, MLT `7.17.0`, 17 playlists, 11 tractors, 17 filters, and 8 transitions. Filter parameters and references such as `red.mpg` are readable. No video was rendered.
- [x] Resolved: does archiving have an implemented asset-path rewrite? The [archive implementation](https://github.com/KDE/kdenlive/blob/80b74ffa95390f4cc8d75a4e886e7ff47373583e/src/project/dialogs/archivewidget.cpp#L964-L1013) rewrites resource, time-warp resource, proxy, and title URLs through its archive mapping. Merely saving the XML therefore differs from collecting the assets; the sampled project references media separately.

Remaining: running an archive/move/restore, missing assets, proxy-only completeness, keyframe/nested-sequence rendering, OTIO losses, and version/crash recovery.

## KeePassXC

- [x] Resolved: what does CSV export actually contain? The [CSV writer](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/format/CsvExporter.cpp#L60-L106) emits ten columns: Group, Title, Username, Password, URL, Notes, TOTP, Icon, Last Modified, Created. It traverses groups but emits no attachment payloads, entry-history records, arbitrary custom attributes, or Auto-Type associations. TOTP is included by this implementation, so it must not be listed as universally absent from CSV.
- [x] Resolved: are attachments and history intrinsically absent from all KeePass XML? The historical [KeePass-generated XML fixture](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/tests/data/NewDatabase.xml) parsed without KeePassXC. It contains six groups, six entries including two historical entries, and two Base64/gzip attachment payloads of 10 and 11 bytes. All four attachment references resolved to those payloads. This is plaintext XML inspection, not decryption of a KDBX vault or a newly executed export.
- [x] Resolved: where is the XML attachment-loss boundary in the inspected CLI path? [`Export`](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/cli/Export.cpp) calls [`Database::extract`](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/core/Database.cpp#L511-L522), which selects a versioned writer through [`KeePass2Writer`](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/format/KeePass2Writer.cpp). [`KdbxWriter::extractDatabase`](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/format/KdbxWriter.cpp) passes an empty binary-index map to the XML writer and disables inner-stream protection. [`KdbxXmlWriter`](https://github.com/keepassxreboot/keepassxc/blob/d5e43b779d5e23c23963d53b806dcda5dd38f50e/src/format/KdbxXmlWriter.cpp#L151-L168) writes binary payloads only for versions below KDBX 4; it still writes attachment references and history. Thus the inspected KDBX 4+ extraction code omits attachment payloads, whereas the older XML representation can embed them. This is a traced source limitation, not an executed export/import test.

Remaining: KDBX decryption in another client, actual CLI export/import on each format version, passkeys, hardware/key-file recovery, merges, and approval/overwrite behavior.
